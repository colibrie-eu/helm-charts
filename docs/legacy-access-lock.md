# Helmvorlage für den Legacy-Cutover

Main führt ausschließlich über die bestehende ArgoCD-Verwaltung aus. Kein Merge, Tag, Deployment oder Ingresszugriff in diesem PR. Chartkandidaten frontend 0.7.22 und onboarding 0.5.8, bisherige Pins 0.7.21 und 0.5.7. Serviceimages derzeit 1.16.38 und 1.2.26. chart-releaser veröffentlicht nach freigegebenem Chartmerge, die manuell synchronisierten Applications übernehmen ohne neuen Pin/Sync nichts automatisch.

Beide Charts geben den booleschen Helmwert `legacyAccessLock.enabled`, Standard false, als zitierte Runtime-Variable LEGACY_ACCESS_LOCK an den Webcontainer. Keine zusätzliche env.LEGACY_ACCESS_LOCK setzen. Helm-Parameter haben Vorrang vor Values-Dateien. Änderungen dieses Werts ändern das Podtemplate und lösen beim manuellen ArgoCD-Sync einen Rollout mit Prozessneuladung aus.

Frontend: aus behält es die bisher konfigurierten HTTP-Proben; an wechseln Liveness/Readiness zu TCP auf dem benannten Containerport http. Damit bleibt die Wartungsantwort 503 auf `/` ohne HTTP-Probenloop möglich. TCP beweist nur den offenen Listener, die externe 503-Seiten-/APIprüfung und interne Anmeldung sind zusätzlich Pflicht. Onboarding: nach ausdrücklicher Main-Vorgabe bleibt GET/HEAD `/healthz` frei, daher bleiben seine HTTP-Proben unverändert. Keine Backend-, Ingress- oder Daemonänderung.

Gemeinsame [Betriebsvorlage im Frontendrepo](https://github.com/colibrie-eu/frontend/blob/feat/wartungssperre-20261016/docs/legacy-access-lock.md): zuerst je Staging-Application neuer Chart/Image mit Gate false plus manueller Sync, danach Gate true mit eigenen Syncs und vollständigem Rückweg; dann Produktion mit neuem Releaseimage/neuem Chartpin und false synchronisieren. Freitag Wert true und manueller Sync je Application. Main-Erfahrung: letzter Start bis Healthy frontend 59 Sekunden, onboarding 26 Sekunden, etwa eine Minute pro Rollout. Bei RollingUpdate antworten alte Pods noch bis zum Abschluss.

Rückweg Aktivierung: gleiche neuen Pins, Wert false, je Application eigener Sync bis Healthy. Kompletter Rückweg: gesicherte vorherige Image-/Chartpins und Parameter/Values gemeinsam wiederherstellen, Gate aus, eigener Sync. Kein vorheriger Frontendchartpin bei weiter aktivem Gate, da die alten HTTP-Proben sonst 503 bekommen. ArgoCD ist manuell, self-heal und prune aus; keine direkte helm-upgrade- oder kubectl-patch-Konkurrenz. Bestehende Ingress-Snippets bleiben unverändert. `/api/v1` wird direkt zum Backend geroutet und bleibt eine ausdrücklich dokumentierte Restgrenze.

`python3 tests/legacy-access-lock.py` prüft die geänderten Probe-/Flagblöcke ohne externe Abhängigkeiten: Auspfad bytegleich zum gepinnten Original, TCP-Block an, HTTP-Proben beim Onboarding unverändert, false als Default und zitierte Runtime-Variable. Zusätzlich wurde der aktive TCP-Block lokal mit dem vorhandenen YAML-Parser gelesen. Das ersetzt kein vollständiges Helmrendern. Lokal fehlt helm, daher vor dem Main-Sync beide Charts mit tatsächlichen Values/Parametern rendern/linten und den ArgoCD-Diff prüfen, ohne Geheimnisse oder Umgebungswerte auszugeben. Testblockwerte sind ausschließlich feste synthetische Schalterzustände.
